# إشعارات الطلبات

حفظ الطلب في قاعدة البيانات يظل الخطوة الأساسية. يُضاف سجل إشعار في نفس معاملة الطلب بعد التحقق من الأسعار والمخزون. لا يُنشأ إشعار لطلب فشل، ولا يُنشأ سجل ثانٍ عند إعادة نفس مفتاح الطلب.

القناة المنفذة حاليًا: **تيليجرام**. أُرسِل سؤال لاختيار القناة، واستخدم تيليجرام كخيار مبدئي أثناء انتظار الإجابة. واتساب التلقائي لم يُربط؛ روابط واتساب اليدوية الحالية مستمرة.

## تفعيل تيليجرام

1. افتح [BotFather الرسمي](https://t.me/BotFather)، وأرسل `/newbot` وأنشئ بوتًا للمتجر.
2. ضع التوكن في `.env.local` داخل المشروع؛ لا تضعه في الكود أو Git أو متغير يبدأ بـ`NEXT_PUBLIC_`.
3. افتح محادثة خاصة مع البوت الذي أنشأته وأرسل `/start garbalia`.
4. شغّل `npm.cmd run notifications:telegram-chat`. سيعرض رقم المحادثة الخاصة التي أرسلت النص المحدد فقط. لا يعرض التوكن أو رسائل العملاء.
5. أضف رقم محادثتك، ثم أعد تشغيل السيرفر:

```dotenv
ORDER_NOTIFICATION_CHANNELS=telegram
TELEGRAM_BOT_TOKEN=your_private_bot_token
TELEGRAM_CHAT_ID=your_private_chat_id
```

عند تفعيل القناة، ستُرسل أيضًا إشعارات الطلبات المنتظرة التي سُجلت **بعد إضافة الميزة**. لا يتم توليد إشعارات تلقائيًا للطلبات القديمة السابقة للميزة. وجّه البوت لمحادثتك الخاصة لأن الإشعارات تحتوي بيانات العملاء.

الإعداد الحالي لا يحتوي توكن أو Chat ID فعليًا؛ لذلك الطلبات تُحفظ والإشعارات تنتظر الإعداد دون إرسال خارجي. اختبارات الإرسال تستخدم محاكاة فقط.

## محتوى الرسالة

رقم الطلب ووقت التسجيل وحالته وقت الإرسال، الاسم والموبايل والعنوان والملاحظات، أسماء المنتجات وألوانها وكمياتها، إجمالي المنتجات والشحن والإجمالي النهائي والدفع عند الاستلام. إذا كثرت البنود يُذكر الباقي في الإدارة للحفاظ على حد الرسالة. لا تُستخدم صياغة Markdown/HTML كي لا تُفسر مدخلات العميل كتنسيق.

يُضاف رابط الإدارة فقط إذا كان APP_URL يبدأ بـHTTPS؛ عنوان localhost لن يفتح على هاتف صاحب المتجر. لا يؤكد الإشعار الطلب، ولا يرسل رسائل للعميل.

## التنفيذ وإعادة المحاولة

- محاولة إرسال بعد انتهاء استجابة الطلب باستخدام Next.js `after`، مع معالجة خلفية كل دقيقة أثناء تشغيل السيرفر.
- الحالات داخل تفاصيل الطلب في لوحة الإدارة: بانتظار الإرسال، جاري الإرسال، تم قبول الإشعار، تعذّر الإرسال. «تم قبول» تعني قبول Telegram API وليست إثبات قراءة المستخدم.
- لا تؤثر مشكلة الشبكة أو التوكن أو المحادثة على حفظ الطلب أو المخزون.
- ٨ محاولات تلقائية مع انتظار متزايد واحترام مهلة 429 من تيليجرام. بعدها يظهر زر إعادة المحاولة للأدمن بعد إصلاح الإعدادات.
- قفل لمدة دقيقتين ومعرّف محاولة يمنعان عاملين من معالجة الإشعار في الوقت نفسه. المحاولات العالقة تُستعاد بعد انتهاء القفل. تُثبّت وجهة المحادثة عند أول محاولة، فلا تُرسل إشعارات قديمة لرقم مختلف عند تغيير الإعدادات.
- الإرسال الخارجي لا يضمن exactly-once: لو قبل تيليجرام الرسالة ثم انقطع الرد، أو توقف السيرفر قبل تسجيل النجاح، قد تصل نسخة أخرى عند إعادة المحاولة. رقم الطلب يظل نفسه ولا يُنشأ طلب إضافي.
- إيقاف السيرفر أو الجهاز يوقف العامل المحلي؛ الإشعارات تظل محفوظة وتُستكمل عند التشغيل. النشر serverless يحتاج عاملًا مجدولًا خارجيًا.
- `npm.cmd run notifications:send` يعالج دفعة واحدة. مع PGlite أوقف خادم الموقع أولًا قبل هذا الأمر كي لا تفتح عمليتان نفس ملفات القاعدة.
- لضبط الإشعارات الجديدة على الإيقاف استخدم `ORDER_NOTIFICATION_CHANNELS=`. إيقافها لا يحذف السجلات السابقة، ويوقف أيضًا إرسالها حتى إعادة التفعيل.

## تحديث قاعدة موجودة

أوقف السيرفر، شغّل `npm.cmd run setup:local` لتطبيق `database/002-notifications.sql`، ثم ابنِ وشغّل الموقع. الإعداد لا يحذف الطلبات أو يعيد ضبط المنتجات. جدول الإشعارات داخل schema خاص، مع RLS وسحب صلاحيات PUBLIC. التوكن لا يُحفظ في جدول الإشعارات ولا تظهر استجابات المزوّد الخام في سجل الأخطاء.

المراجع: [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage)، [إنشاء بوت](https://core.telegram.org/bots/features#botfather)، [Next.js after](https://nextjs.org/docs/app/api-reference/functions/after).
