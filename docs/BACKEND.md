# Garbalia — تشغيل الطلبات والإدارة محليًا

النسخة الحالية تحفظ الطلبات والمنتجات والمخزون والصور المرفوعة في قاعدة PostgreSQL محلية عبر [PGlite](https://pglite.dev/docs/). هذه قاعدة بيانات داخل عملية Node واحدة، وليست localStorage في المتصفح. المسار الافتراضي `.data/store`، وهو مستبعد من Git وغير منشور في `public`.

## التشغيل والحساب

1. `npm.cmd ci`
2. أوقف أي خادم يستخدم قاعدة المشروع، ثم شغّل `npm.cmd run setup:local` مرة واحدة.
3. `npm.cmd run build` ثم `npm.cmd run start`، أو `npm.cmd run dev` للتطوير.

الإعداد ينشئ `.env.local` إن لم يوجد، ثم الجداول والمنتجات المبدئية الثمانية وحساب إدارة بكلمة مرور عشوائية. بيانات الحساب في `.local-admin.txt` بجذر المشروع. لا تنشر هذا الملف. إعادة الإعداد لا تعيد ضبط المخزون ولا تكتب فوق المنتجات المعدلة أو الحساب الموجود.

المتجر: `http://127.0.0.1:3000` — الإدارة: `http://127.0.0.1:3000/admin`.

لا تشغّل خادمي تطوير/إنتاج، أو أوامر إعداد/انتهاء مهلة، على **نفس قاعدة PGlite** في وقت واحد. الاختبارات تنشئ قواعد مستقلة تلقائيًا داخل `.cache`.

## تسجيل الطلب

- طلب ضيف بالدفع عند الاستلام. البيانات المطلوبة: الاسم، موبايل مصري صالح، محافظة من القائمة، المدينة والعنوان؛ الملاحظات اختيارية.
- السيرفر يستقبل هوية المنتج واللون والكمية فقط مع الإجمالي الذي شاهده العميل؛ يقرأ السعر والمخزون من قاعدة البيانات. إذا تغيّر السعر يرفض الطلب ويطلب مراجعة الإجمالي.
- تكلفة واحدة للطلب: ٨٠ للقاهرة والجيزة و١٢٠ لباقي المحافظات. تفاصيل الشحن تظهر في الدفع فقط بالمتجر العام.
- إنشاء الطلب، حفظ أسماء وأسعار وصور بنوده، وحجز المخزون يتم في معاملة واحدة. الفشل يرجع كل التغييرات. قفل الصفوف وترتيب التعامل معها يمنع بيع آخر قطعة مرتين.
- مفتاح UUID لكل محاولة يمنع التكرار بعد انقطاع الاتصال أو النقر المتكرر. إعادة المفتاح مع بيانات مختلفة تُرفض. آخر ملخص طلب ومفتاح المحاولة وبصمتها فقط محفوظة في sessionStorage؛ اسم العميل وعنوانه وموبايله لا تُحفظ هناك.
- ملخص النجاح يُعرض بعد تأكيد الحفظ من السيرفر، ويحفظ رقم الطلب والمبالغ دون بيانات العميل. الملخص في المتصفح ليس شاشة تتبع لحظية للحالة.

## المخزون وانتهاء المهلة

قرار صاحب المتجر: الطلب الجديد **بانتظار التأكيد** ويحجز الكمية، ويُلغى تلقائيًا إذا مرّت ٢٤ ساعة دون تأكيد.

- المؤقت يفحص الطلبات كل دقيقة أثناء تشغيل Node. بعد إغلاق الجهاز لا تعمل مهمة محلية؛ عند إعادة تشغيل السيرفر، أو قراءة الكتالوج/الطلبات أو إنشاء طلب، تُعالج الطلبات المنتهية.
- تعود الكمية مرة واحدة فقط، ويُسجل سبب الإلغاء في تاريخ الطلب. الطلبات المؤكدة/قيد التجهيز مستثناة من المهلة.
- التأكيد يدوي من لوحة الإدارة؛ فتح واتساب وحده لا يؤكد الطلب.
- الحالات: بانتظار التأكيد ← قيد التجهيز ← تم الشحن ← تم التسليم. الإلغاء اليدوي متاح قبل الشحن. التحصيل حالة منفصلة تُسجل بعد التسليم.
- عند تعديل مخزون منتج، يُرفض النموذج القديم إذا تغيّر المنتج أو مخزونه منذ فتحه، لتجنب الكتابة فوق حجز حديث.

`npm.cmd run orders:expire` يشغّل المعالجة مرة واحدة. للقاعدة المحلية أوقف السيرفر أولًا؛ للنشر السحابي يحتاج هذا الأمر مُجدولًا مستقلًا كل دقيقة. الحد ١٠٠ طلب في الدورة، مع استمرار الدورات اللاحقة لمعالجة أي تراكم.

## لوحة التحكم

- دخول بكلمة مرور مشفرة باستخدام scrypt، وجلسة عشوائية مخزنة كبصمة SHA-256، عمرها ٨ ساعات، في cookie من نوع HttpOnly وSameSite=Strict. تستخدم Secure عند ضبط APP_URL على HTTPS.
- عرض آخر ٢٠٠ طلب وتصفيتها، تفاصيل العميل والبنود، سجل الحالة، التأكيد/الإلغاء والتجهيز والتسليم والتحصيل.
- إضافة وتعديل وإخفاء المنتجات، الأسعار والوصف والتصنيف والصور والمخزون لكل لون. الإخفاء يحفظ تاريخ الطلبات السابقة.
- إضافة التصنيفات وفروعها. حذف/إعادة ترتيب التصنيفات ليس ضمن هذه النسخة.
- الصور المرفوعة تحفظ في قاعدة البيانات وتُعرض من `/media/[id]`؛ PNG/JPEG/WebP ثابتة، حتى ٤ ميجابايت و٦٠٠٠ بكسل، مع فحص تنسيق الصورة. لا تُقبل SVG أو عناوين صور خارجية.
- رقم المتجر `01028673770`؛ روابط واتساب تفتح رسالة جاهزة فقط. إرسالها يظل إجراءً يدويًا.

## حدود الوصول

إشعارات الطلبات الجديدة تستخدم جدولًا مستقلًا ضمن نفس معاملة الطلب، مع عامل إرسال ومحاولات تلقائية وصفحة حالة في تفاصيل الطلب. الربط المجهز هو تيليجرام، ويظل الإرسال متوقفًا حتى إضافة توكن البوت ورقم المحادثة. لا تتأثر الطلبات بفشل الشبكة. راجع [docs/NOTIFICATIONS.md](NOTIFICATIONS.md)، وطبّق `database/002-notifications.sql` عبر الإعداد المحلي قبل تشغيل النسخة الجديدة.

كل مسار يغيّر بيانات الإدارة يفحص الجلسة وOrigin. مسار الطلب العام يفحص المدخلات والحدود ومصدر الطلب ويقيّد معدل المحاولات. لا يوجد endpoint عام لسرد الطلبات أو بيانات العملاء. الجداول في schema خاص `garbalia` مع RLS مفعّل وصلاحيات PUBLIC مسحوبة؛ الاتصال يتم من السيرفر فقط.

خلف proxy موثوق يزيل رؤوس الزائر ويستبدلها يمكن تفعيل `TRUST_PROXY=1` لحدود المحاولات حسب عنوان العميل. محليًا يستخدم التطبيق حدًا مشتركًا؛ لا تثق برأس `x-forwarded-for` من الإنترنت مباشرة.

## الاختبارات

```powershell
npm.cmd run lint
npm.cmd run typecheck
npm.cmd run test:server
npm.cmd run build
npm.cmd run test:e2e
```

اختبارات الخادم تستخدم قاعدة مستقلة، والمتصفح يشغّل خادم اختبار تلقائيًا على 3001 بقاعدة وحساب اختباري مستقلين. لا تحتاج لتغيير مخزون المتجر أو مسح طلباته. ملفات الاختبار ولقطات الشاشة في `.cache` و`test-results`.

التحقق المنفذ: ١٦ اختبار خادم، و٢١ اختبار متصفح ناجح مع اختبار قائمة الموبايل متجاوز على الديسكتوب. التزامن اختُبر على PGlite محليًا؛ مسار الاتصال بـPostgres/Supabase السحابي لم يختبر على حساب فعلي بعد.

## النشر لاحقًا

اختار صاحب المتجر التجهيز المحلي أولًا. `garbalia.com` مرجع تصميم، وليس نطاقًا مملوكًا للمشروع. لم يتم نشر الموقع أو توصيل Supabase.

يمكن ضبط `DATABASE_URL` لاتصال PostgreSQL/Supabase خاص بالسيرفر عبر TLS، ثم تطبيق `database/001-store.sql` وتهيئة البيانات والحساب في البيئة المستهدفة. لا تستخدم PGlite على قرص مؤقت في استضافة serverless. عند الانتقال: اضبط APP_URL وHTTPS، حساب الإدارة الإنتاجي، جدولة المهلة، النسخ الاحتياطية، وحدود proxy، ثم أعد الاختبارات على قاعدة النشر.

سياسات الاستبدال والاسترجاع والخصوصية ومدة التوصيل والعنوان لم يحددها صاحب المتجر بعد، لذلك لم تُنشر سياسات افتراضية. المنتجات والصور والأسعار ما زالت مبدئية. البيع الحقيقي يتطلب استكمالها قبل الإطلاق.

على Windows يزيل التطبيق سمة القراءة فقط من مجلدات قاعدة البيانات المحددة قبل فتحها، لمعالجة سمة يضيفها OneDrive وتفسرها PGlite كمنع للكتابة. لا يعيد إنشاء القاعدة ولا يمسح بياناتها. يتضمن التحقق اختبار إغلاق وفتح قاعدة محفوظة بعد محاكاة هذه السمة.
